● I've read through all eight documents. Here's what they describe:

  Core idea — A visual flow-based language where control flow is "turned inside
  out": instead of scoped blocks, iteration/branching/scopes are represented as
  flow identity wires that can be opened ($/Uncollect), closed (@/Collect),
  bundled, joined, commuted, and case-split. Flows are first-class, distinct
  from value wires.

  Three layers in the design:
  1. Language layer (visual-language-spec.md, flow_language_design.md,
  visual-flow-language.md) — A Diagram containing Nodes whose NodeKind is one of
   ~22 variants (Literal, Primitive, Uncollect, Collect, Bundle, Join, Commute,
  Incorporate, IterationRail, TapOut, etc.). Inputs are ValueSource/FlowSource
  references pointing to outputs of other nodes — a DAG.
  2. Graph layer (graph-representation.md) — A semantics-free layout
  intermediate: Graph, Node, Array, OutputLogicalPort/InputLogicalPort with
  rightOf constraints, VisualPort for geometry, Edge with a containment-path
  source, plus port/node annotations.
  3. Transformation + rendering (program-to-graph-transformation.md,
  rendering-algorithm.md, visual-layout-guidelines.md) — How to map (1)→(2),
  then the 12-step layered drawing algorithm.

  Key invariants worth modelling:
  - "No time travel": flow nesting/ordering established at construction time;
  that's why Join/Commute take both flows and values as inputs.
  - Each flow type (iteration / alternative / opaque / effect) supports a
  different subset of operations.
  - IterationRail + TapOut use RailReference.ById to express loop-carried state
  without structural cycles.
  - The graph layer deliberately has no semantic types — it only knows geometry
  and constraints.

  Ready for the next step. Want me to start sketching data structures for a
  particular slice of this (e.g., just the language layer, or just the graph
  layer), or do you want to point me at a specific feature to explore first?
